# Your environment: a personal cloud sandbox VM

You are running inside a dedicated AWS Lambda MicroVM that belongs entirely to
this user and is reached through a browser terminal. Act accordingly: you have
far more freedom here than in a typical local checkout, and different
persistence rules.

## What you can do freely
- Full shell as `coder` with passwordless sudo. Installing packages (dnf, npm,
  pip), running servers, compiling, long builds — all fine, no approval needed.
- Outbound network from Bash is fully open (curl, git clone, package registries).
- This VM is isolated per user: nothing you run here can affect other users.

## What persists (and what does not)
- ONLY `/home/coder` persists. It is an NFS mount backed by Amazon S3, scoped
  to this user, and it survives VM restarts and recycles.
- `npm install -g` persists: the npm prefix is `~/.npm-global` (on PATH), so
  global npm installs land in home and survive recycles — no sudo needed.
- `pip install` also persists: pip falls back to `--user` (`~/.local`, on
  PATH) when system site-packages isn't writable.
- Everything else — `sudo dnf install`, `uv tool install` (kept on /opt, see
  below), system config — is on the VM image and resets when the VM is
  recycled. If the user needs such a tool long-term, add the install command
  to `~/.zshrc` so it self-heals on a fresh VM.
- The home filesystem rejects hardlinks (EMLINK). Tools that depend on them
  should keep caches/state outside home: uv is already configured for /opt/uv;
  point similar tools at /tmp or /opt if they fail oddly in $HOME.

## VM identity
- `$MICROVM_ID` is this VM's id; `$MICROVM_ENDPOINT` is its public HTTPS
  ingress URL (both also in /tmp/microvm-id and /tmp/microvm-endpoint).
  The endpoint reaches port 8080 (the terminal) and requires a proxy auth
  token — it is NOT a way to expose arbitrary services publicly.

## Credentials and AWS access
- Each CLI authenticates with the user's own provider login, persisted under
  the home directory (`~/.claude`, `~/.codex`, `~/.kiro`, `~/.config/opencode`).
- The VM starts with no AWS credentials. To use AWS, authenticate as the user
  inside the VM, for example `aws sso login --no-browser`, `aws configure sso`,
  or an existing profile. Credentials and profiles persist under `~/.aws` in
  the home.
- The VM's own IAM role is limited to the S3 Files mount and an endpoint
  lookup, so it grants nothing against the user's accounts.
- `gh` (GitHub CLI) is installed. Sign in over HTTPS with the device flow:
  `gh auth login --git-protocol https --web`. It prints a URL and a one-time
  code; open the URL (Cmd/Ctrl-click it in the terminal) and enter the code.
  The session persists under `~/.config/gh`. With a personal access token
  instead: `echo $TOKEN | gh auth login --with-token`.
- There is no inbound SSH server, and no way to reach one: the VM is only
  reachable through the browser terminal and `tools/exec.js`. The SSH client is
  installed for outbound use, so `git@github.com:...` works if you add a key
  under `~/.ssh`; `gh` over HTTPS is simpler for GitHub.

## VM lifecycle — checkpoint long work
- Idle is measured by INBOUND browser traffic only. If the user closes the tab,
  the VM suspends after a period of inactivity (your process freezes
  mid-instruction and resumes later; in-flight network calls will have died, so
  retry). A VM is also terminated after a maximum lifetime.
- For long-running jobs, write progress and results to files under /home/coder
  as you go. Files survive termination; your session does not.

## Web search and fetching
- The native web search and fetch tools are available. Use them for current
  information and cite your sources.
- For fetching a specific page from Bash, curl also works, e.g.:
  curl -s "https://example.com"  or  curl -s "wttr.in/London?format=3"
